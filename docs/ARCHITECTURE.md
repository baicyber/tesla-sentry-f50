# 架构与实现原理

## 1. 整体数据流

```
                  ┌─────────────────────────────────────────────┐
  特斯拉车机        │            小 Linux 设备                     │
┌──────────┐      │                                             │
│ Sentry   │ USB  │  ┌──────────────────────────────────────┐   │
│ Clips    │◄────►│  │ USB Gadget (configfs)                │   │
│ 写入      │      │  │  ├─ ncm.usb0   ← USB 虚拟网卡         │   │
└──────────┘      │  │  ├─ acm.GS0    ← 串口控制台           │   │
                  │  │  └─ mass_storage.0 ← 虚拟U盘          │   │
                  │  └───────────────┬──────────────────────┘   │
                  │                  │ lun.0/file = $TSF_IMG     │
                  │                  ▼                          │
                  │      teslacam.img (exFAT, 稀疏, 默认64G)     │
                  │        │                     │               │
                  │        │ os.pread 只读       │ 车闲置 > IDLE  │
                  │        │ (每 15 秒)          │ (仅写音频时)   │
                  │        ▼                     ▼               │
                  │  tesla-live-sync.py    tesla-sync.sh:       │
                  │   按 exFAT 解析,        unbind UDC → mount → │
                  │   带 .pruned 墓碑       写 Boombox 音频 →    │
                  │   + 滚动窗口过滤        umount → rebind      │
                  │        │                                     │
                  │        ▼                                     │
                  │      /archive (ext4, 日志式) ──► sentry-viewer.py :8080
                  └─────────────────────────────────────────────┘
```

**关键设计**：镜像（exFAT）与归档区（ext4）是两块**物理隔离**的存储。车机永远只碰镜像，网页永远只碰归档区，两者不会同时读写同一个 exFAT 文件系统。

## 2. 为什么能"伪装 U 盘"

Linux 内核的 USB Gadget 框架允许设备扮演 USB 外设。通过 configfs（`/sys/kernel/config/usb_gadget/`）可以动态拼装一个复合设备：

| 功能 | configfs 路径 | 作用 |
|---|---|---|
| NCM | `functions/ncm.usb0` | USB 虚拟网卡（SSH/网页访问） |
| ACM | `functions/acm.GS0` | 串口控制台（救援用） |
| Mass Storage | `functions/mass_storage.0` | 虚拟 U 盘（本项目追加） |

`mass_storage` 的 `lun.0/file` 指向一个**普通文件**，主机就会把它当作块设备。所以"64G U 盘"其实是设备上的一个稀疏文件。

> 注意：修改 gadget 必须先 `echo "" > UDC` 解绑，**解绑期间所有 USB 功能（网卡、串口、U 盘）会同时消失**。因此所有涉及解绑的操作必须脱离 SSH 会话执行（`setsid`），否则命令会被自己掐断。

## 3. 归档与同步 (v2.7.0 起)

**视频走在线只读同步，定时挂载脚本不再复制事件目录。**

```
tesla-live-sync.py (常驻, 默认 15 秒一轮)
  1. 拿 flock 共享锁 (网页管理/定时归档持排他锁时跳过本轮)
  2. 只读打开 teslacam.img, 按 exFAT 规范解析引导扇区/FAT/目录项 (os.pread)
  3. 连续两轮 (DataLength, ValidDataLength, mtime) 一致才认为片段写完
  4. 跳过 /archive/.pruned 墓碑里的事件 (盒子侧已清理的)
  5. RecentClips 只收滚动窗口内 (TSF_RECENT_ROLL_MIN, 默认 60 分钟)
  6. 拷到 /archive/<cat>/<事件名>/
  -> 全程不 mount、不写镜像, 车机无感

tesla-sync.sh (cron, 每 10 分钟; 只负责写 Boombox 音频)
  1. 拿 flock 排他锁; 拿不到直接跳过 (不排队堆积)
  2. 镜像 mtime 距今 < IDLE(600s) → 车还在写, 退出
  3. 解绑 UDC → losetup → mount -t exfat (读写)
  4. 把 boombox-queue/ 音频写到镜像根目录, 成功后移到 boombox-done/
  5. umount → losetup -d → 重新绑定 UDC
```

**为什么定时脚本不再复制视频**：车机 U 盘上仍留着盒子侧已清理的旧事件，"目录不存在就 `cp -r`"会把它们重新抄回来，形成 删除→重抄 死循环（`.pruned` 里同一事件被重复登记、归档日志反复写满磁盘）。现在归档规则只有一份，就在 `tesla-live-sync.py` 里。

**为什么还要短暂断开**：写音频需要往 exFAT 镜像里写，而 exFAT 不是集群文件系统，同一时刻只能有一端挂载。视频同步是只读解析，不受此限制。

**为什么只在空闲时挂载**：行车/哨兵录制期间镜像 mtime 持续更新，永远不会满足"空闲 600 秒"，所以不会打断录制。停车熄火后若队列里有音频，才会在约 10 分钟后挂载一次，全程 5–15 秒。

## 4. 断电与数据安全

车内 USB 口在车辆休眠时会**硬断电**，没有优雅关机。

| 风险 | 缓解 |
|---|---|
| 正在写镜像时断电 → exFAT 损坏 | 镜像只由车机写（车机的写入是它自己的事）；Linux 侧只在归档窗口内挂载，且挂载前先解绑 UDC，避免双写 |
| 音频写入中断 → 半个文件 | 只有 cp 成功才把音频移出队列；失败则留在 queue，下轮重试 |
| 归档区断电损坏 | 归档区用 ext4（日志式），掉电后 fsck 自愈 |
| 镜像彻底损坏 | 删掉镜像重建即可（车机会重新格式化，历史事件已在归档区） |

## 5. 网页 U 盘管理模式（状态机）

```
         POST /api/usb/attach                POST /api/usb/detach
IDLE ───────────────────────► MANAGE ─────────────────────────► IDLE
  ▲      unbind UDC              │         umount + detach
  │      losetup + mount rw      │         + rebind UDC
  │                              │
  └──────────────────────────────┘
        5 分钟无操作自动 detach (threading.Timer)
```

- 网页挂载、定时归档、U盘自愈、在线同步共用 `/tmp/tsf-usb.lock`：前三者持排他锁，在线同步持共享锁；任一方持锁时其它入口自动跳过，不再出现并发抢 loop 设备与挂载点
- 查看器进程启动时会自愈：先短暂重试拿锁，拿到才 umount、detach loop、重新绑定 UDC；拿不到则完全不碰 U 盘
- 所有写操作后立即 `sync`，再恢复导出，避免缓存丢失

## 6. 安全边界

| 入口 | 限制 |
|---|---|
| `/api/browse`、`/dl`、`/api/file` | 路径 realpath 必须以 `/archive` 开头，防 `../` 逃逸 |
| `/api/usb/browse`、`/usbdl`、`/api/usb` | 路径 realpath 必须落在镜像挂载点内 |
| 上传 | 单文件 ≤ 100MB；文件名仅允许 `[\w\-. ]`，自动去除目录部分 |
| 音频 | ≤ 1MB（车机限制）；锁车音必须 WAV |

**没有内置身份认证**。请只在内网使用，公网暴露请自行加反向代理认证或走 VPN。

## 7. 播放器布局与同步策略

布局按事件实际路数自适应，不写死路数：

| 车型 | 路数 | 布局 |
| --- | --- | --- |
| Model 3 / Model Y（HW3） | 4 | 2×2：第 1 排 前视 + 后视，第 2 排 左B柱 + 右B柱 |
| Model S / X、HW4 车型 | 6 | 3×2：第 1 排 左前翼 + 前视 + 右前翼，第 2 排 左B柱 + 后视 + 右B柱 |

左右摄像头固定在同一列，前后固定在同一排，方位感与实车一致。缩略图拼图与播放器共用同一套排序。

同步方面，各路视频独立解码，以第一路为基准，每 250ms 校正一次：任何一路与基准偏差 > 0.35s 就 `currentTime` 对齐。这比"同时 play()"更稳，能消化不同编码器的启动延迟差异。

## 8. 内嵌遥测（SEI）解码

Tesla 在**车辆行驶中录制**的片段里，会把行车数据作为 SEI（H.264 NAL type 6）逐帧写进码流。数据跟着文件走，因此不需要任何云端账号、不需要车机联网，只要有视频就有遥测。停车状态下录制的哨兵片段大多不含 SEI，此时播放页的遥测面板自动隐藏，其余功能不受影响。

解码流程（全部标准库，无第三方依赖）：

1. 按 mp4 box 结构定位 `moov/trak/mdia/minf/stbl`，读 `stsz` / `stco` / `stsc` 还原每个样本的偏移与长度；NAL 长度前缀字节数取自 `avcC`（第 9 字节低 2 位 + 1）
2. 逐样本按长度前缀切出 NAL，筛出 `type == 6`；去掉防竞争字节（`00 00 03` → `00 00`）
3. 跳过 SEI 头，定位 magic `0x42 0x69` 之后的 protobuf `SeiMetadata`，手写 varint / fixed32 / fixed64 解码
4. 默认每 3 帧取一条（`stride=3`），按 `帧号/fps` 换算成秒；结果以「文件路径 + 大小 + mtime」的 md5 为键缓存在 eMMC，二次读毫秒级

字段对应（`SeiMetadata`，字段号 → 含义）：

| # | 字段 | # | 字段 |
| --- | --- | --- | --- |
| 1 | 版本 | 9 | 刹车是否踩下（布尔） |
| 2 | 挡位 | 10 | 自动辅助驾驶状态 |
| 3 | 帧序号 | 11 | 纬度 |
| 4 | 车速（m/s） | 12 | 经度 |
| 5 | 油门踏板（%） | 13 | 航向角 |
| 6 | 方向盘角度 | 14 | 横向加速度 Ax |
| 7 | 左转向灯 | 15 | 前后加速度 Ay |
| 8 | 右转向灯 | 16 | 垂直加速度 Az |

注意：**刹车在数据源里只有"踩下/未踩"的布尔量**，没有踏板开度。因此页面上刹车不显示百分比，只显示一枚「刹车」状态徽章（踩下时变红），导出水印同理；油门是真实连续百分比。

## 9. 镜像区与归档区

两份数据并存，用途不同：

| 区域 | 路径 | 写入方 | 读取方 |
| --- | --- | --- | --- |
| 镜像区（虚拟 U 盘） | `teslacam.img` | 车机 | 车机、插上的电脑 |
| 归档区 | `/archive` | 归档任务从镜像拷出 | 网页查看器 |

网页只读归档区，因此「网页上有、U 盘里没有」属于正常现象：归档是镜像的副本，不是同一份数据。

需要把归档内容反向写回镜像（做演示盘、恢复数据）时，必须走 `scripts/tesla-img.sh`：

```sh
sh tesla-img.sh exec 'cp -r /archive/SentryClips/2026-11-04_12-30-00 /tmp/imgrw/TeslaCam/SentryClips/'
```

脚本会先 detach LUN 再挂载镜像写入，避免主机侧 FAT / 目录缓存与设备侧写入互相覆盖。

## 10. 已知限制

- 编码实测为 **H.264 High 1280×960**（2022 Model Y / 本仓库开发车）；部分新车型或新固件改用 HEVC，浏览器需相应解码支持（Edge/Chrome 需系统 HEVC 扩展，Safari 原生支持）
- SEI 遥测并非每段都有：**行驶中录制**的片段基本每帧都有，**停车状态**的哨兵片段大多没有。没有时遥测面板隐藏，属数据源缺失而非解析失败
- 刹车只有布尔量（没有踏板开度），面板只给「刹车」状态徽章不给百分比；方向盘、油门为真实连续值
- 单线程 HTTP 服务器（`ThreadingHTTPServer`），并发播放多路视频会吃 CPU；遥测解码首次约 0.3–0.5s/段（24s 片段），命中 eMMC 缓存后毫秒级
- 归档以"事件目录"为单位，未做增量文件级同步
- USB 3.0 总带宽与 eMMC 写入速度决定录制稳定性；实测 eMMC 写 80–130MB/s，哨兵写入峰值仅 20–40MB/s
